## Approach

This repo's layout will mostly fall out of how the user consumes the published packages in
`pubspec.yaml`, and what we publish to pub.dev. The directory structure partly follows from them.

Spec references:

- [Overview](https://opentelemetry.io/docs/specs/otel/overview/) — package types: API, SDK, Semantic Conventions, Contrib
- [Client Design Principles](https://opentelemetry.io/docs/specs/otel/library-guidelines/) — API/SDK separation, exporters
- [Resource SDK](https://opentelemetry.io/docs/specs/otel/resource/sdk/) — resource detector packaging

## Goal: dirt simple for developers

It won't be simple for us, but it must be for users.

A Dart developer's `pubspec.yaml`, at its simplest:

```yaml
dependencies:
  opentelemetry: ^1.0.0
```

A Flutter developer's:

```yaml
dependencies:
  opentelemetry_flutter: ^1.0.0
```

A library author instrumenting their own package (native instrumentation):

```yaml
dependencies:
  opentelemetry_api: ^1.0.0
```

## No Separation of Signals

Python, .NET, Rust, Erlang and Swift all ship a single API and a single SDK.

Other languages such as Java and JavaScript publish signals separately.
* For JavaScript, it's important to publish signals separately to reduce web app bundle size.
* For Java, this seems mostly historical since signals reached maturity at separately.

Dart should publish all signals together because:
* The Dart AOT compiler "tree shakes". If a signal is not used, it won't be compiled in.
* All 3 signals have equal maturity.
* It's simpler for Dart and Flutter developers, and OTel contributors and maintainers.

Two burdens:
- We need to have tests that ensure Dart and Flutter apps that don't use signals are indeed smaller by the expected amount. (A dependency matrix analzer can help.)
- What do we do about the Profile signal, or other new signals, where do we implement them?  Recommendation - alpha and beta signals can ride along, documented as such. This is common in other packages (Android).

Given this, the package layout is easier.

## Spec constraints

The spec overview tells us that there are 5 artifact types:
1. Semantics
2. API
3. SDK
4. Other Core - exporters
5. Contrib - these are integrations of two kinds: API contrib and SDK contrib.

### Semantics
Semantics clearly get published separately.

For the repo layout, there are two directories for semantics.
1. The package directory that publishes all common and federated semantics, generated by Weaver.
2. The spec directory for Dart and Flutter federated semantic definitions, consumed by Weaver.

### API

The API clearly must be published separately. It should be one package.

### SDK

The SDK gets published separately from the API. However the 

The library guidelines say:

> The SDK must be clearly separated into wire protocol-independent parts...and
protocol-dependent telemetry exporters.

and also

> The SDK implementation should include the following exporters:
logs, metrics, trace, OTLP (OpenTelemetry Protocol).
Standard output (or logging) to use for debugging and testing as well as an input for the various log proxy tools.
In-memory (mock) exporter that accumulates telemetry data in the local memory and allows to inspect it
(useful for e.g. unit tests), metrics, Prometheus, and Zipkin."

(Aside: Zipkin is deprecated and not planned.)

The guidance does not prescribe a package layout.  The SDK can depend on the exporters separately.

### Exporters vs. "the SDK should include exporters"

The guidelines say the SDK implementation *should include* OTLP, stdout,
in-memory, Prometheus and Zipkin exporters. Read with constraint 4, this is
about what the SDK *offering* provides, not that they share one package.
There is no circular dependency:

- `opentelemetry_sdk` defines the exporter interfaces (`SpanExporter`,
  `MetricExporter`, `LogRecordExporter`).
- Exporter packages depend on `opentelemetry_sdk`.
- The entry-point packages (`opentelemetry`, `opentelemetry_flutter`) depend on
  both and wire them together.

The stdout (console) and in-memory exporters have no heavy dependencies and
stay in `opentelemetry_sdk`, as in Java and JS.



## Published packages

| Package                             | Kind                 | Depends on                       | Notes                                                                                                                    |
|-------------------------------------|----------------------|----------------------------------|--------------------------------------------------------------------------------------------------------------------------|
| `opentelemetry_api`                 | API                  | —                                | Pure Dart, no `dart:io`. No-op by default.                                                                               |
| `opentelemetry_sdk`                 | SDK                  | api                              | Exporter interfaces, processors, samplers, console + in-memory exporters, generic resource detectors. Platform-agnostic. |
| `opentelemetry_semantics`           | Semantic conventions | —                                | Weaver-generated.                                                                                                        |
| `opentelemetry_exporter_otlp`       | Core exporter        | sdk, protobuf, http              | Protos, transformers, OTLP/HTTP (protobuf + JSON), config, gzip, user agent, cert utils, HTTP client factory. Web-safe.  |
| `opentelemetry_exporter_otlp_grpc`  | Core exporter        | exporter_otlp, grpc              | Split out so HTTP-only and web builds never see `dart:io`/grpc.                                                          |
| `opentelemetry_exporter_prometheus` | Exporter             | sdk                              |                                                                                                                          |
| `opentelemetry`                     | Dart entry point     | api, sdk, exporter_otlp          | Re-exports api + sdk. `OTel.initialize()`.                                                                               |
| `opentelemetry_flutter`             | Flutter entry point  | api, sdk, exporter_otlp, Flutter | Re-exports api + sdk. `FlutterOTel.initialize()`, Flutter resource detection, lifecycle.                                 |

Dependency graph:

```
opentelemetry_api
      ▲
opentelemetry_sdk
      ▲
opentelemetry_exporter_otlp ◄── opentelemetry_exporter_otlp_grpc (optional)
      ▲
      ├── opentelemetry            (Dart)
      └── opentelemetry_flutter    (Flutter)
```

### Why both `opentelemetry` and `opentelemetry_flutter`

Flutter is to Dart what Android is to Java. `opentelemetry-android` is a
separate package layered on the Java SDK that handles initialization,
platform resource detection and bundled RUM instrumentation. At minimum the
Flutter package differs in:

- **Initialization:** `FlutterOTel.initialize()` vs `OTel.initialize()`. Not
  spec-defined, but the developer-facing entry point.
- **Resource detection:** screen size, device manufacturer, model, etc.
  Constraint 5 requires these to live outside the SDK.

Both entry points are thin; everything shared lives in the SDK and exporters.

### Semantic conventions naming

Other languages use `semconv` (Java, Go) or `semantic_conventions` (Python,
JS, Rust, Erlang). We propose `opentelemetry_semantics`: clearer than
`semconv` and shorter than `semantic_conventions`, which fits Dart package
naming style. This is a deliberate deviation; see open questions.

The package is Weaver-generated. Today it generates from the common semantic
conventions; it must be able to pull in multiple semconv registries as they
become federated.

## Contrib

Contrib is optional instrumentation and plugins maintained by the OTel
project, separate from the SDK:

- **API contrib** depends only on the API.
- **SDK contrib** also depends on the SDK.

Packages hosted outside OTel are third-party, not contrib.

### Existing packages to contribute

Mindful Software published and will contribute to OpenTelemetry the 40–50 open-source `otel_*` packages to pub.dev 
(e.g. `otel_logger`, `otel_go_router`, `otel_serverpod`). Each lives in its own repo
today and uses the same `dart ./tool/release.dart` publishing workflow as the
SDK and API.  

Contributing these to OpenTelemetry gives us a place to work with the
maintainers of the instrumented packages and grow the OpenTelemetry community.
For example, the Serverpod team has reviewed `otel_serverpod` and we plan to work on it together. 
Where a library's maintainers are willing, native instrumentation against
`opentelemetry_api` inside their package is the best outcome; contrib covers
the rest.

## Repo layout

Directory name == pub package name.

```
opentelemetry-dart/
  packages/
    opentelemetry_api/
    opentelemetry_sdk/
    opentelemetry_semantics/
    opentelemetry_exporter_otlp/
    opentelemetry_exporter_otlp_grpc/
    opentelemetry_exporter_prometheus/
    opentelemetry/
    opentelemetry_flutter/
  examples/
    server/
    flutter/
  tool/
  pubspec.yaml        # pub workspace
```

Each package has its own `lib/`, `lib/src/`, `test/`, `example/`,
`CHANGELOG.md` and `README.md`.

## Open questions

1. **Contrib location.** Nearly every language uses a separate
   `opentelemetry-<lang>-contrib` repo, with component owners and independent
   releases. Do we start a separate `opentelemetry-dart-contrib` repo, or put
   contrib under `contrib/` in this repo until it grows?
2. **Contrib naming.** The spec recommends
   `opentelemetry_instrumentation_<lib>` for OTel-hosted instrumentation
   (e.g. `opentelemetry_instrumentation_go_router`). That's long for Dart; the
   existing packages use the Go-style `otel_<lib>`. Erlang contrib uses
   `opentelemetry_<lib>`. Which do we adopt?
3. **Exporter split.** @Carlos Alberto Cortez — does the separation above
   (interfaces in SDK, exporters depending on SDK, entry points wiring both)
   match how other SIGs read the guidelines?
4. **Default gRPC in `opentelemetry`.** Should the Dart entry point depend on
   `opentelemetry_exporter_otlp_grpc` too, or leave it opt-in? Proposal:
   opt-in, pending performance tests. HTTP may be as fast or faster than gRPC
   even server-side.
5. **Flutter.** @Cesar Munoz — your Android experience is very welcome here.
   What belongs in `opentelemetry_flutter` beyond initialization and resource
   detection (lifecycle, navigation, frame timing, sessions, offline
   buffering), and what should be separate contrib packages?
6. **`opentelemetry_semantics`** vs `opentelemetry_semantic_conventions`.
   Deviating from other languages needs consensus.
